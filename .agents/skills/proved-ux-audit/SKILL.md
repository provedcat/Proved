# Proved UX Audit

## Mission

Proved의 목적은 사용자의 판단을 대신하는 것이 아니라, 반려동물 사료를 더 잘 이해하고 비교하고 급여량을 결정할 수 있는 기준을 제공하는 것이다.

이 스킬의 1차 목표는 **실제 사용자 여정에서 마찰·혼란·불신·이탈 지점을 찾아 개선하는 것**이다.
2차 목표는 UX 개선을 통해 다음 행동을 늘리는 것이다.

- 첫 방문자가 핵심 기능을 이해하고 실제로 사용하기
- 검색/조건찾기에서 상세·비교·계산기로 자연스럽게 이동하기
- 사료가 없을 때 등록 요청 후 원래 작업으로 복귀하기
- 결과를 저장·공유하고 다시 방문할 이유가 생기기
- 정보의 출처·기준·한계를 이해해 서비스 신뢰를 형성하기

방문 증가를 단순 트래픽 숫자로만 해석하지 않는다. 직접적으로 통제 가능한 UX 지표인 **활성화, 과업완료율, 다음 단계 이동률, 재방문 의도, 공유 가능성, 검색 실패 복구율**을 우선 개선한다. 다크패턴, 과도한 알림, 강제 회원가입, 허위 긴급성으로 체류나 클릭을 늘리지 않는다.

## Runtime requirements

이 스킬은 검사 절차와 판단 기준이다. 실제 사용자 여정 검증에는 가능한 경우 브라우저/Computer Use를 함께 사용한다.

브라우저가 있으면 반드시 실제 화면에서 다음을 수행한다.

1. 클릭
2. 텍스트 입력
3. 검색
4. 필터 선택/해제
5. 스크롤
6. 뒤로가기/앞으로가기
7. 새로고침
8. 모바일/데스크톱 폭 확인
9. 로딩/빈 상태/오류 상태 확인
10. 주요 단계 스크린샷 비교

브라우저가 없으면 코드 기반 점검이라고 명시하고, 실제 여정 검증을 했다고 주장하지 않는다.

## Sources of truth

검사 전 다음 우선순위를 따른다.

1. `DESIGN.md`의 현재 `PD-*` 규칙
2. 현재 main 브랜치 실제 동작
3. 이 스킬의 `journeys.md`
4. 이 스킬의 `audit-rubric.md`
5. 최신 명시적 제품 결정

`DESIGN.md`와 충돌하는 오래된 UI 관습은 재도입하지 않는다.

## Audit modes

### A. Full journey audit

사이트 전체 핵심 사용자 여정을 검사한다. 기본 모드다.

### B. PR regression audit

PR에서 변경된 화면과 연결된 이전/다음 단계까지 검사한다. 변경 파일만 보는 코드 리뷰로 끝내지 않는다.

예: 사료등록 페이지 변경이라면 등록 페이지 자체뿐 아니라
`계산기 → 사료 없음 → 등록 → 완료 → 계산기로 복귀 → 자동 선택/검색 복원`
까지 확인한다.

### C. Focused surface audit

사용자가 특정 화면을 지정한 경우 해당 화면을 깊게 검사하되, 진입 경로와 다음 행동까지 최소 1단계씩 포함한다.

## Core audit loop

각 사용자 여정은 아래 순서로 검사한다.

### 1. Establish user intent

화면 이름이 아니라 사용자의 목적을 한 문장으로 정의한다.

예:
- "내 고양이에게 맞는 후보 사료를 빠르게 좁히고 싶다."
- "두 사료의 차이를 판단할 근거를 보고 싶다."
- "현재 급여 조합으로 하루에 몇 g을 줘야 하는지 알고 싶다."

### 2. Run the happy path

처음 방문한 사용자처럼 설명 없이 수행한다. UI가 다음 행동을 스스로 설명해야 한다.

### 3. Run recovery paths

최소 다음 실패/변형 상황을 검사한다.

- 검색 결과 없음
- 사료 미등록
- 일부 영양정보 없음
- 동일 브랜드 제품 두 개 비교
- 긴 제품명
- 많은 조건 태그
- 느린 등록 처리
- 새로고침
- 뒤로가기
- 모바일 작은 화면

### 4. Inspect transition quality

각 단계 사이에서 다음을 묻는다.

- 사용자가 지금 어디 있는지 아는가?
- 방금 한 행동의 결과를 알 수 있는가?
- 다음에 무엇을 해야 하는지 명확한가?
- 이전 단계에서 입력/선택한 상태가 보존되는가?
- 같은 정보를 다시 입력하게 만들지는 않는가?
- 기다리는 이유와 진행 상태를 이해할 수 있는가?

### 5. Inspect decision quality

Proved는 평가 점수를 강요하지 않는다. 사용자가 판단하기 위한 정보가 다음 원칙을 지키는지 본다.

- 사실 / 기준 / 해석이 구분되는가
- 정보가 없으면 `정보 부족`, `확인되지 않음`, `—` 등으로 정직하게 표시되는가
- 숫자의 단위와 비교 기준이 명확한가
- 빨간색이나 승자 표시로 근거 없는 우열을 만들지 않는가
- 핵심 숫자와 보조 숫자의 위계가 명확한가

### 6. Inspect visual hierarchy

`DESIGN.md`의 적용 가능한 `PD-*` 규칙을 반드시 확인한다.
특히 다음은 매번 검사한다.

- SUIT Variable 통일
- 제목 Proved Blue, 제목 검정색 금지
- 공유 header/subnav/footer 사용
- 의미 없는 카드 모자이크 금지
- 과한 radius/pill/shadow 금지
- semantic data color 보존
- accidental horizontal overflow 금지
- 모바일은 데스크톱 축소판이 아니라 재구성
- touch target 최소 44px
- reduced motion 대응

### 7. Inspect growth loops

각 핵심 과업 완료 후 서비스 안에서 자연스러운 다음 가치가 있는지 본다.

- 상세를 봤다면 비교로 이어질 이유가 있는가
- 비교했다면 급여량 계산으로 이어질 이유가 있는가
- 계산했다면 저장/공유/재확인 가치가 있는가
- 등록했다면 원래 작업으로 복귀하는가
- 유용한 결과를 다시 찾기 쉬운가

강제 CTA를 추가하기 전에 **사용자가 이미 만든 데이터·결과·선택을 다음 가치로 연결할 수 있는지**부터 본다.

## Proved-specific invariants

다음은 회귀 시 높은 우선순위로 본다.

### Condition Finder

- 폴더는 같은 x/y 위치에서 겹치고 선택 시 z-axis 앞으로 이동한다.
- 모든 탭은 계속 클릭 가능해야 한다.
- 긴 태그는 폴더 내부 스크롤로 처리하고 페이지 전체 높이를 무한히 늘리지 않는다.
- 선택 수는 흰 badge가 아니라 탭 라벨의 일부로 보여야 한다.
- 태그는 직접 toggle이며 재클릭 시 해제된다.
- 여러 태그 결과는 AND/intersection 의미를 유지한다.

### Food Detail

- Product Tag Blob은 제품의 태그를 요약하는 signature visual이어야 하며 장식물이 아니다.
- 기본정보 grid는 값이 없어도 구조를 유지하고 누락값을 명시한다.
- 모바일 energy / water / Ca:P는 compact metric strip으로 유지한다.
- DM/등록값을 우선하고 기준 라벨 반복으로 수치가 묻히지 않아야 한다.

### Compare

- 정확히 2개 제품 비교를 기본으로 한다.
- 같은 브랜드 두 제품 비교 시 A/B만으로 구분하지 말고 제품명 차이를 강조한다.
- Proved가 승자를 선언하는 UI를 만들지 않는다.
- 정보 부족을 추정으로 채우지 않는다.

### Calculator

- 읽기/DOM/시각 순서는 `01 급여 중인 사료 → 02 반려동물 정보 → 03 급여 비율 → 04 계산 결과`.
- 결과의 주인공은 각 사료의 g이다.
- kcal는 보조정보다.
- 인터랙티브 결과의 Ca/P와 수분 분석은 유지한다.
- 저장/공유 이미지는 흰 배경의 간결한 문서이며 화면 전체 분석을 그대로 복사하지 않는다.

### Feed registration loop

사료 미등록은 막다른 길이 아니라 복구 가능한 사용자 여정이어야 한다.

반드시 검사할 흐름:

`계산기/검색 → 사료 없음 → 사료 등록하기 → FEED REGISTRATION → 처리중 → 등록 완료 → return_to 복귀 → pendingRegisteredFeed 복원 → 가능한 경우 자동 선택 / 아니면 검색어 채움`

검사 항목:

- 등록 링크가 의도치 않게 새 탭을 열지 않는가
- 원래 페이지/슬롯/종류 정보를 잃지 않는가
- 처리 중 반복 클릭이 막히는가
- 약 13초 연구 동안 구체적인 진행 상태가 보이는가
- 짧은 주황색 주의 문구가 있는가
- 완료 후 뒤로가기 했을 때 등록 화면이 다시 튀어나오지 않는가
- 복귀 후 등록한 제품을 다시 처음부터 찾게 만들지 않는가

### Feed Reading / Editorial

- 설명은 자연스러운 문단과 중앙 정렬 규칙을 따른다.
- 강제 `<br>`로 이상한 줄바꿈을 만들지 않는다.
- 차트/인포그래픽은 개념 설명을 돕기 위한 것이며 장식용 이미지를 채우지 않는다.

## Device matrix

주요 변경이나 전체 감사 시 가능한 범위에서 다음 폭을 확인한다.

- 1440
- 1024
- 980
- 768
- 390
- 375

최소한 desktop 1개 + mobile 1개는 실제 렌더로 검증한다.

## Severity

### P0 — Blocker

핵심 과업 불가능, 데이터 오판 위험, 잘못된 결과 저장/표시, 진행 불가.

### P1 — Major

완료는 가능하지만 높은 이탈/오판 가능성이 있는 문제. 상태 손실, 등록 후 복귀 실패, 모바일 주요 CTA 접근 불가, 같은 제품 오인 등을 포함한다.

### P2 — Moderate

사용자가 멈칫하거나 반복 행동하게 만드는 문제. 정보 위계, 불명확한 문구, 불필요한 단계, 좁은 터치영역, 일부 반응형 문제.

### P3 — Minor

완료율에 큰 영향은 적지만 일관성·완성도·신뢰감을 떨어뜨리는 문제.

우선순위는 심각도만으로 정하지 않는다. 다음을 함께 본다.

`Priority = severity × frequency × journey_criticality × confidence`

## Evidence rule

모든 발견은 가능한 한 증거를 붙인다.

- URL/route
- viewport
- 재현 단계
- 기대 동작
- 실제 동작
- 스크린샷 또는 화면 관찰
- 관련 `PD-*` 규칙
- 관련 코드 파일/함수

관찰하지 않은 것은 관찰했다고 쓰지 않는다.

## Output format

감사 결과는 단순 감상평이 아니라 실행 가능한 개선 백로그로 작성한다.

### 1. Journey verdict

각 여정별로:

- 완료 여부
- 가장 큰 마찰
- 가장 큰 개선 기회

### 2. Findings table

각 finding에 다음 필드를 포함한다.

- ID
- Severity
- Journey
- Screen/route
- Evidence
- Why it matters
- Recommended fix
- Related `PD-*`
- Suggested owner area (HTML/CSS/JS/data)

### 3. Growth impact hypothesis

개선안마다 어떤 행동 변화가 예상되는지 명시한다.

예:
- 검색 실패 → 등록 → 복귀를 단축하면 계산기 과업완료율 상승 가능
- 비교 제품 식별성을 높이면 잘못된 비교 이탈 감소 가능
- 저장 결과 가독성을 높이면 공유/재방문 가치 상승 가능

인과를 검증하지 않은 상태에서 "방문자가 증가한다"고 단정하지 않는다.

### 4. Fix order

먼저 고칠 3~5개를 제시한다. 디자인 완성도보다 핵심 여정의 단절·상태손실·오판 위험을 우선한다.

### 5. Verification plan

수정 후 재검사할 정확한 단계와 viewport를 적는다.

## Do not

- 화면을 예쁘게 만드는 것을 UX 개선과 동일시하지 않는다.
- 모든 문제를 새 카드/새 모달/새 CTA로 해결하지 않는다.
- 사용자를 더 오래 붙잡기 위한 마찰을 만들지 않는다.
- 회원가입을 핵심 기능 사용 전에 강요하지 않는다.
- 정보가 없는 곳에 확신하는 문구나 점수를 만들지 않는다.
- 기존 Proved signature interaction을 일반 SaaS 패턴으로 평준화하지 않는다.
- 브라우저 검증 없이 "PC/모바일 모두 확인"이라고 보고하지 않는다.

## Completion criteria

UX audit가 완료되었다고 말하려면 최소 다음이 있어야 한다.

- 하나 이상의 실제 사용자 intent 기반 journey 수행
- happy path + 하나 이상의 recovery path 확인
- desktop/mobile 또는 환경 제한 명시
- severity가 붙은 구체적 finding
- `DESIGN.md` 관련 규칙 검토
- 재검증 가능한 수정 제안

전체 감사라면 `journeys.md`의 Tier 1 여정을 모두 수행해야 한다.
